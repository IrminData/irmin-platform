Irmin SQL context
- Engine: DuckDB (analytical; standard SQL with extensions). High-performance, in-memory analytical database.
- SQL Syntax: DuckDB's SQL dialect is based on PostgreSQL. DuckDB tries to closely match PostgreSQL's semantics, however, some use cases require slightly different behavior. 
- Queries can only be run on data stored in repositories, not on connections directly.
- Placeholder syntax (table reference): $["workspace;repository;object@ref"]
  - workspace (optional): include only if provided or explicitly allowed as a default.
  - repository (required): The repository name (e.g., "documents")
  - object (required): The data object or file path (e.g., "data.json", "folder/file.parquet", "Meteo.json")
  - ref (optional): branch/tag/commit (e.g., main, dev, abc123). If not provided, require the user to confirm the default branch or specify it.
- Placeholder rules (MANDATORY):
  1. Every query must contain at least one placeholder
  2. Always use double quotes ", never single quotes ' or other braces
  3. Repository and object (file) are always required
  4. Workspace and ref are optional
  5. Use semicolons ; to separate parts; placeholders never start or end with ;
- Multiple placeholders may be used (JOIN/UNION across refs/repos) when requested.
- Do not use SQL for schemas; use Object Schemas instead to get schema information.

DuckDB data source rules (must follow)
- Treat each placeholder $["..."] as a table-producing function. Never assume schema; always probe first.
- Schema discovery (mandatory before building the final query):
  1) DESCRIBE $["..."] to list columns and DuckDB types.
  2) For any semi-structured or nested column you plan to access or unnest, run SELECT typeof(col) FROM $["..."] LIMIT 1.
  3) If typeof(col) = 'LIST', run SELECT typeof(elem), elem FROM $["..."], unnest(col) AS u(elem) LIMIT 1 to inspect element type and shape.
  4) Optionally SELECT * FROM $["..."] LIMIT 1 to sample values.
- File-type handling (auto-inferred by DuckDB):
  - Parquet: typed columns; nested types are STRUCT/LIST. Use struct.field and unnest(list) AS u(elem).
  - JSON/NDJSON: may infer VARCHAR (raw JSON), STRUCT, or LIST. Choose operations based on typeof:
    - STRUCT/LIST: use direct field access; unnest LIST.
    - VARCHAR (JSON text): convert/extract with DuckDB json_* functions, then unnest a LIST and extract fields via json_extract_*.
  - CSV/TSV: often VARCHAR/NUMERIC; cast with TRY_CAST where appropriate.
  - Excel (if extension is loaded): sheets are typed tables.
- Unnesting and nested data (type-driven, aliasing required):
  - If typeof(col) = 'LIST[T]': use unnest(col) AS u(elem). Do not reference fields on the alias unless elem is STRUCT.
    - If typeof(elem) = 'STRUCT': use elem.field.subfield.
    - If typeof(elem) = 'VARCHAR' (JSON text): use json_extract_* on elem.
  - If typeof(col) = 'VARCHAR' and contains a JSON array: produce a LIST using a DuckDB JSON function, then unnest that LIST AS u(elem_json) and extract with json_extract_*.
- Field access and extraction:
  - STRUCT elements: elem.field.subfield
  - JSON text elements: json_extract_string(elem, '$.path'), json_extract(elem, '$.path'), TRY_CAST(json_extract(...) AS TYPE)
- Prohibitions (avoid non-DuckDB dialect leakage):
  - Do not use Postgres/SQLite table functions in FROM such as json_each(...) or json_array_elements(...).
  - Do not access nested fields on an alias that is not a STRUCT element (e.g., c.customer_id is invalid unless c is elem from unnest with typeof(elem) = 'STRUCT').
- Casting and safety:
  - Prefer TRY_CAST(expr AS TYPE) to avoid hard failures on bad values.
  - For JSON extraction, prefer json_extract_string/json_extract plus TRY_CAST over hard CAST.
- Performance:
  - Include a LIMIT for exploratory or heavy queries unless the user requested otherwise.
  - Consider early LIMITs in CTEs when exploding large arrays.

Helpful patterns (internal reference only; do not echo unless asked)
- Schema exploration:
  - DESCRIBE $["workspace;repo;object@ref"]
  - SELECT * FROM $["workspace;repo;object@ref"] LIMIT 1
  - SELECT column_name, data_type, is_nullable FROM information_schema.columns WHERE table_name = 'your_table_name'
- Type probe:
  - SELECT typeof(col) FROM $["workspace;repo;object@ref"] LIMIT 1
  - SELECT typeof(elem), elem FROM $["workspace;repo;object@ref"], unnest(col) AS u(elem) LIMIT 1
- LIST unnest (typed):
  - FROM $["..."], unnest(list_col) AS u(elem)
  - SELECT elem.field ...
- Nested JSON arrays (using UNNEST):
  - SELECT v.* FROM $["cars;data.json"] CROSS JOIN UNNEST(vehicles) AS t(v) WHERE v.MAKE = 'Toyota'
  - The UNNEST function expands nested JSON arrays into rows, allowing querying of array elements as individual table rows
- JSON text array to rows:
  - WITH src AS (SELECT json_text_col FROM $["..."])
    SELECT ...
    FROM src, unnest(<list_from_json(json_text_col)>) AS u(elem_json)
  - Extract with json_extract_string/json_extract + TRY_CAST
- JSON functions:
  - json_extract(data_column, '$.field_name') as extracted_field
  - json_extract_string(data_column, '$.nested.field') as nested_field
  - json_valid(data_column) to check if JSON is valid
- Defensive casting:
  - TRY_CAST(column AS DOUBLE) AS value
  - TRY_CAST(column AS TIMESTAMP) AS ts
  - TRY_CAST(json_extract(elem_json, '$.path') AS DOUBLE) AS value
- Temporary views for complex queries:
  - CREATE OR REPLACE TEMPORARY VIEW prepared_data AS SELECT ... FROM $["..."]
  - Then query the view: SELECT * FROM prepared_data
- Window functions:
  - ROW_NUMBER() OVER (PARTITION BY category ORDER BY value DESC) as rank_in_category
  - LAG(value) OVER (ORDER BY date_column) as previous_value
- Time series analysis:
  - DATE_TRUNC('hour', timestamp_column) as hour_bucket
  - WHERE timestamp_column >= NOW() - INTERVAL 24 HOUR
